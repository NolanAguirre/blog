Dependency inversion at all levels

Development June 08, 2026
Dependency Inversion has a specific meaning in SOLID. This post uses it more loosely, as a lens for thinking about the direction of dependencies.

The concept

Dependency inversion is a concept that comes from the land of object-oriented programming. My first exposure to it was from one of Uncle Bob's speeches on SOLID principles. This kicked off my thinking of the term in a broader context.

The basic idea within SOLID is that high-level code should not depend directly on low-level implementation details.

To me dependency inversion is just one example of a broader design move: making volatile implementation details depend on stable abstractions instead of the other way around. That idea shows up in classes, services, queues, APIs, and sometimes functions — but applying it blindly creates ceremony and over-engineering.

The class level

This is the classic example. If you're writing OOP and don't know about SOLID principles, I'd highly recommend this article: Robert C. Martin's original principles page.

Worst:

class ReportGenerator {
  printToHpPrinter(report) {
    // HP-specific printing logic
  }

  printToCanonPrinter(report) {
    // Canon-specific printing logic
  }
}

Bad:

ReportGenerator ---depends on---> HpPrinter
ReportGenerator ---depends on---> CanonPrinter

Good:

ReportGenerator ---depends on---> Printer interface <---implements--- HpPrinter
                                                    <---implements--- CanonPrinter

In the worst version, the high-level business logic and the low-level printer details are mixed together in the same class. Moving printer-specific behavior into separate classes is better, but ReportGenerator still depends directly on concrete printer implementations.

The dependency-inverted version keeps the behavior the same: a report still gets printed by a real implementation. But the source-code dependency has changed direction. The business logic depends on a stable abstraction instead of directly depending on printer-specific implementation details.

In non-OO languages, I would consider this the package or module level. For example, if you're integrating with a third-party payment provider, the core payment logic should depend on a small payment-provider contract instead of directly depending on Stripe, Adyen, or any other concrete provider. Each provider implementation should expose the same function names and arguments, as if it were implementing an interface.

The architecture level

With how powerful dependency inversion is, what happens if we apply the same concept to software systems instead of just classes?

This is one of my favorite things to do. Keeping systems loosely coupled makes it easier to iterate on one side of an abstraction while keeping the blast radius small.

So, how does this OO principle look at the architecture level?

So you could have:

Service One --Calls-> Service Two

Technically, if Service One and Service Two share a message contract, then you have the same diagram as "good" from above, but that is changing levels down to the implementation level. I'd like to keep the dependency inversion more at the architecture level, so what does that look like?

Service One --Queues Message-> Queue <-Pulls-- Service Two

The important shift is not merely that there is a queue. The important shift is that Service One no longer needs Service Two to be running. In the direct call version, Service Two being down means Service One either fails, retries, blocks, or has to carry all of that failure-handling logic itself.

With the queue in the middle, Service One can keep chugging along. The queue becomes the backpressure boundary between the systems. Service Two can be slow, down, overloaded, or mid-deploy, and Service One can still accept work and hand it off safely.

That is the architecture-level version of changing the dependency direction. Service One is no longer operationally dependent on Service Two. The two services still need the implementation-level dependency inversion of relying on a shared contract for code quality and maintainability.

The function level

Now, admittedly, this is where the "Dependency Inversion" concept starts to fall into the realm of over-engineering. If you take the idea too literally in JavaScript, you could end up doing something like this:

import { EventEmitter } from 'node:events'

const eventEmitter = new EventEmitter()

function foo(x) {
  eventEmitter.emit('bar', x + 1)
}

function bar(x) {
  console.log('bar received:', x)
}

eventEmitter.on('bar', bar)

foo(1)

But, this is verbose. Technically foo is no longer dependent on bar, but at what cost? Additionally, imagine doing this with a date formatting function; that's just crazy.

The function level is already the level where abstractions happen a lot; abstraction is the keystone of functions. You move the logic of some code into its own function so you can change the implementation without having to modify multiple call sites. The specific pattern of dependency inversion doesn't apply here.

I think the closest thing to dependency inversion I've encountered at the function level is something like Redux, and it's not strictly dependency inversion. I also largely think Redux is over-engineered; things approaching this level of abstraction are generally not what I pursue.

Having functions with their arguments is the contract that dependency inversion seeks to enforce at a higher level; the function is the abstraction that is depended on, not the logic within.

The opcode level

Could we keep going lower? What does dependency inversion look like at the opcode level? 

ADD R1, R2

It doesn't. At some point the framing stops being useful. The CPU is not asking for an IAddInstruction abstraction.

The takeaway

The goal is not to invert every dependency. Any idea applied dogmatically to all things is problematic. The goal is to notice which dependencies are stable, which are volatile, and whether the current direction of dependency makes the system easier or harder to change.

Sometimes that means an interface. Sometimes it means a queue. Sometimes it means passing behavior as an argument. And sometimes it means doing nothing, because the direct dependency is the right dependency.
